> 이 서식 그대로 씁니다. 자유롭게 쓰지 않습니다 — 서식이 곧 작업대(CLAUDE.md · 일꾼 파일)로 옮겨지는 통로입니다.
> 예약어 셋: **동시에**(나눔) · **통과할 때까지**(되돌림) · **사람 확인 후**(관문). 상한: 종류 3~5 · 일꾼 3~5 · 대본 5~8줄.

이름: ______________  소재: ☐ A 고객 문의 ☐ B 사내 요청 ☐ C 콘텐츠 의뢰 ☐ 내 업무: ______________

## ① 접수 분류표 — 누구에게 보내나 (게이트 배정)

> **왜 이 칸인가** — 정의만 쓰면 겹친다. **제외** 칸이 종류 사이의 경계를 긋고, **예시** 두 문장이 분류 AI의 기준점이 된다. **기타**가 없으면 모르는 요청이 아무 데나 간다 — 기타의 끝은 사람.

```
[가드레일] 들어오면 거절하는 것 (위험 · 개인정보 · 범위 밖):
  - ______________________________
  → 거절 문구 1줄, runs/에 "거절" 기록

[종류 1] ______ 요청
  정의: ______를 해 달라는 것
  포함: ______, ______
  제외: ______ (→ 종류 _) / ______ (→ 기타)
  예시: "______________" / "______________"
  → 담당: ______ 일꾼

[종류 2] ______ 요청
  정의:
  포함:
  제외:
  예시: "" / ""
  → 담당: ______ 일꾼

[종류 3] ______ 요청
  정의:
  포함:
  제외:
  예시: "" / ""
  → 담당: ______ 일꾼

[기타] 위 어디에도 맞지 않으면 → 사람. runs/에 "사람 확인 필요 + 원문" 남기고 멈춘다
[섞임] 두 종류에 걸치면 → 쪼개서 둘 다. 순서는 지휘 대본 S-_ 에 적는다
[되묻기] 종류를 못 가리겠으면 질문 한 개, 한 번만 → 그래도 모르면 기타
```

**스스로 점검** — ☐ 종류끼리 겹치지 않는가(제외 칸이 서로를 가리키는가) ☐ 올 수 있는 요청을 다 덮는가 ☐ 기타가 있는가 ☐ 종류마다 예시 2개

## ② 일꾼 카드 — 한 명 = 한 가지 일 = 지침 한 장 (조종사)

> **왜 이 칸인가** — 일꾼끼리는 머리를 공유하지 않는다. **받는 것**에 없는 건 일꾼이 모른다. **내는 것의 양식**이 있어야 다음 일꾼이 읽는다. **완료 조건**이 없으면 "됐다"를 모른다. **내 일 아님**이 있어야 잘못 온 요청을 돌려보낸다.

```
이름: ______ 일꾼
맡는 일(한 줄): ______________________________
받는 것: 요청 원문 + ______________
내는 것(양식): 제목 / 본문 / 근거 / 확신도(상·중·하) / 미처리 사항
완료 조건: ______________________________
내 일 아님: ______이면 "재라우팅 요청"으로 돌려보낸다
```

```
이름: ______ 일꾼
맡는 일(한 줄):
받는 것:
내는 것(양식):
완료 조건:
내 일 아님:
```

```
이름: ______ 일꾼
맡는 일(한 줄):
받는 것:
내는 것(양식):
완료 조건:
내 일 아님:
```

(검토가 필요한 일이면) 
```
이름: 검토 일꾼
맡는 일: ______의 내는 것이 ______에 어긋나지 않는지 본다
받는 것: ______ 일꾼의 내는 것
내는 것: 통과 / 수정 요청(이유 1줄)
완료 조건: 둘 중 하나
```

**스스로 점검** — ☐ 일꾼마다 내는 것 양식이 있는가 ☐ 그 양식을 다음 일꾼이 읽을 수 있는가 ☐ 완료 조건이 있는가 ☐ 내 일 아님이 있는가

## ③ 지휘 대본 — 어떤 순서로 잇고 누가 책임지나 (관제탑)

> **왜 이 칸인가** — 관제탑은 비행기를 몰지 않는다. 대본에는 **순서 · 상태 · 호출**만 — 판단 문장("~이면 좋게", "~를 잘")이 들어가면 두꺼운 관제탑. 예약어 셋으로 나눔·되돌림·관문을 표시한다.

```
관제탑 규칙:
  - 직접 처리하지 않는다. 반드시 담당 일꾼에게 보낸다
  - 한 단계 끝날 때마다 runs/<날짜_요청>/에 한 줄: 담당 · 받은 것 · 낸 것
  - 바퀴 상한 __ · 되묻기는 요청당 1회

S-1 (종류 1): ______ 일꾼에게 요청 원문을 넘긴다 → 내는 것이 양식대로 나오면 끝, 아니면 F-1
S-2 (종류 2): ______ 일꾼에게 → 끝 / ______이면 F-_
S-3 (종류 3): ______ 일꾼이 만들고 → 검토 일꾼이 통과할 때까지 (최대 _바퀴) → 사람 확인 후 끝
S-4 (섞임 _+_): ______ 일꾼 먼저 → 그 결과 파일을 ______ 일꾼에게 → 끝
S-5 (종류 _): ______ 일꾼과 ______ 일꾼에게 동시에 → 둘 다 나오면 합쳐서 끝
S-6 (갈림): ______ 일꾼 결과가 ____이면 S-_, 아니면 S-_
```

**스스로 점검** — ☐ 판단 문장이 없는가 ☐ 바퀴 상한·되묻기 횟수가 있는가 ☐ 사람 확인 후가 돈·밖·되돌릴 수 없음 앞에 있는가 ☐ 섞임 종류마다 S-줄이 있는가

---

## ④ 실패 각본 — 회항 절차는 이륙 전에 적는다

> **왜 이 칸인가** — 실패는 반드시 온다. 미리 적지 않으면 관제탑이 그 자리에서 판단하고(두꺼워지고), 기록 없이 멈춘다. 재시도 · 되돌리기 · 멈춤 · 부분 성공 — 넷 중 하나로 끝나야 한다.

```
F-1 내는 것이 양식에 안 맞음 → 같은 일꾼에게 "양식대로 다시" 1회 → 그래도 아니면 F-9
F-2 일꾼이 "내 일 아님" → 접수 분류표로 되돌려 다시 분류 1회 → 그래도 아니면 F-9
F-3 바퀴 상한 도달 → 지금까지 된 것만 내고 "미완" 표시(부분 성공) → F-9
F-4 되묻기에 답이 없음 → ______________ → F-9
F-9 사람에게 → runs/에 "사람 확인 필요 + 멈춘 단계 + 원문" 남기고 멈춘다
```

**스스로 점검** — ☐ 모든 S-줄의 "아니면"이 F-번호를 가리키는가 ☐ F-9(사람)로 끝나는가 ☐ 재시도 횟수가 적혀 있는가
