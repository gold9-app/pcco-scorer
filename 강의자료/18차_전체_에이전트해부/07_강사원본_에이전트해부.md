## §A. 해부도 원본 — 작업대 위 에이전트 한 채

### A-1. 슬라이드 25에 보여주는 트리 (수강생용 — 이름만)
```
접수-에이전트/
  CLAUDE.md            ← 지휘자의 규칙(순서·상태·호출) + 보내는 표(라우팅)
  일꾼/
    소재.md · 성과.md · 일정.md     ← 일꾼 한 명 = 지침 한 장(15차 I-MRKO 형식)
  inbox/               ← 들어오는 요청(txt 한 건 = 한 파일)
  runs/                ← 기록: 누가 받았고 뭘 냈나
```

### A-2. 작업대(Claude Code) 실제 대응표 (강사만 — 슬라이드에 없음)
| 오늘의 이름 | 작업대에서의 실물 | 비고 |
|---|---|---|
| 지휘자의 규칙 + 보내는 표 | `CLAUDE.md` (폴더 루트) | 세션 전체에 적용되는 규칙. 라우팅 표를 **글로** 적는다 — "요청이 inbox에 오면 아래 표대로 담당에게 보낸다. 직접 하지 않는다" |
| 일꾼 | `.claude/agents/<이름>.md` (서브에이전트 정의) | 파일 하나 = 일꾼 하나. 맨 위 frontmatter(name·description)와 본문 지침. **별도 컨텍스트**에서 실행 — 부모 대화·부모가 읽은 파일을 모른다. 결과(요약)만 부모에게 돌아온다 |
| 감독 패턴 | 부모 세션이 서브에이전트를 호출하는 것 | 오늘 "감독 = 맡기고 결과만 받는다"의 실물 |
| 스킬 | `.claude/skills/<이름>/SKILL.md` | 필요할 때 읽는 절차 문서. 일꾼이 아니라 일꾼이 참고하는 매뉴얼 |
| 손 | Read · Write · Edit · Bash 등 내장 도구 | 모델이 매 턴 어느 도구를 쓸지 고른다 = 라우팅 ② |
| MCP | `.mcp.json` 등으로 꽂는 외부 도구 | 8차 "USB" |
| 기록 | `runs/<날짜_요청>/` 폴더 | CLAUDE.md 규칙으로 "처리 후 반드시 runs/에 요약 한 줄을 남긴다"를 명시해야 남는다 |
| 사람 관문 | 규칙 + (실제 운영에선 permission 설정) | 오늘은 개념만 — "외부 발송·삭제 전엔 사람 확인" 규칙 한 줄 |

### A-3. 수강생용 트리에서 **일부러 뺀 것** (질문이 나오면 한 번만 답한다)
- `.claude/` 폴더 이름 — "작업대 안의 실제 폴더 이름은 다음 실습 회차에서. 오늘은 '일꾼 폴더'로 충분"
- frontmatter·description — "일꾼 파일 맨 위에 이름표 두 줄이 있는데, 그것도 다음 회차"
- permission·hook — 사람 관문의 실제 장치. 오늘 범위 밖

### A-4. CLAUDE.md 예시 (강사 리허설용 — 수강생에게 띄우지 않는다)
```
# 접수 에이전트 — 지휘자 규칙

## 임무
inbox/ 에 들어온 요청을 종류별로 담당 일꾼에게 보내고, 결과를 runs/ 에 남긴다.

## 규칙 (얇게 — 순서·상태·호출만)
- 직접 처리하지 않는다. 반드시 아래 표대로 담당에게 보낸다.
- 담당이 처리한 결과를 받아 runs/<날짜_파일명>/결과.md 로 저장하고, 맨 위에 "담당: ○○ 일꾼" 한 줄을 쓴다.
- 두 일꾼을 거쳐야 하면 앞 일꾼의 결과 파일 경로를 뒤 일꾼에게 넘긴다.

## 보내는 표 (라우팅)
| 종류 | 분류 기준 | 담당 |
|---|---|---|
| 소재 요청 | 새 이미지·문구·배너를 만들어 달라는 것 | 소재 일꾼 |
| 성과 질문 | 이미 집행한 것의 숫자(CTR·전환·비용)를 묻는 것 | 성과 일꾼 |
| 일정 조율 | 날짜·시간을 맞추자는 것 | 일정 일꾼 |
| 섞인 요청 | 두 종류에 걸치면 — 성과 먼저, 그 결과로 소재 | 성과 → 소재 |
| 모르는 요청 | 위 어디에도 안 맞으면 | runs/ 에 "사람 확인 필요" 로 남기고 멈춘다 |
```

## §B. 깊이 설명 전문 (러닝시트 📌 "깊이(강사용)"의 원문 — 질문이 나오면 한 줄로 답하고 슬라이드로 복귀)

### B-1. 컨텍스트 윈도우 (슬라이드 10)
모델이 한 번에 처리하는 글의 양(토큰 단위). 넘치면 앞부분이 잘리거나(잊은 것처럼 행동), 비용·지연이 급증한다. 긴 대화일수록 앞의 규칙을 '잊은 것처럼' 행동하는 이유. 해법은 요약·파일화·분리 — 오늘의 '나눈다'가 곧 이것. 서브에이전트가 별도 컨텍스트를 갖는 것도 같은 이유(각자 머리를 작게 유지).

### B-2. 루프의 멈춤 규칙 (슬라이드 08)
실제 루프 = 모델이 도구 호출을 결정 → 작업대가 도구 실행 → 결과를 모델에 돌려줌 → 모델이 다음 호출 또는 종료를 결정, 의 반복. 운영에선 종료 조건·최대 반복 수·비용 상한을 둔다. 한 줄: "루프에도 멈추는 규칙이 있다 — 안 그러면 돈이 돈다."

### B-3. 워크플로 vs 에이전트 (슬라이드 04)
프로그램(순서를 사람이 정함)과 에이전트(순서까지 모델이 정함) 사이에 '워크플로'를 두는 분류가 있다 — 정해진 순서 안에서 LLM이 각 칸만 채우는 것. 오늘은 셋으로만 가른다. 질문이 나오면 "프로그램이 순서를 정하고 LLM이 칸을 채우면 워크플로, 순서까지 LLM이 정하면 에이전트" 한 줄. 8차 영상 공장은 엄밀히는 워크플로에 가깝다(순서 고정) — 그래서 "줄 패턴"의 실물로 쓴다.

### B-4. 모델 라우팅 (슬라이드 13 ③)
분류·추출처럼 정답이 좁은 일은 소형 모델(빠르고 저렴 — 10배 이상 차이가 흔함), 긴 생성·복잡한 추론은 대형 모델. 흔한 설계 = **캐스케이드**: 작은 모델이 먼저 하고 확신도가 낮으면 큰 모델로 넘긴다. 한 줄: "같은 일꾼 안에서도 쉬운 일은 싼 머리, 어려운 일은 비싼 머리 — 그것도 보내는 표의 한 줄."

### B-5. 의미 검색 · 임베딩 (슬라이드 14 ③)
글을 숫자 좌표로 바꿔 '가까운' 과거 요청을 찾는 방식. 규칙(글자 일치)도 분류 AI(판단)도 아닌 셋째 길. 과거 사례와 그때의 라우팅 결과가 쌓여 있어야 작동 → 운영 초기엔 못 쓴다. 실무는 규칙 → 분류 AI → 의미 검색 순으로 섞는 경우가 많다(규칙으로 거르고 남은 것을 AI가).

### B-6. 확신도 · 핸드오프 (슬라이드 15)
**확신도**: 분류 AI에게 "종류 + 확신 0~1"을 함께 내게 하고 임계값(예: 0.7) 아래면 사람 경로로. **핸드오프**: 일꾼이 '내 일 아님'을 구조적으로 표현하는 것 — 결과 대신 "재라우팅 요청"을 돌려주게 지침에 적는다. 둘 다 03 카드 질문 ④의 실무판.

### B-7. 채점기 라우팅의 실체 (슬라이드 17)
채점기는 '모드 값 → 루브릭 프롬프트 선택'의 **규칙 방식**. 분류 AI가 아니므로 오분류가 없지만 "버튼이 있어야 한다"는 비용을 사용자가 낸다. 버튼 없이 자연어로 받으면 분류 AI가 필요해진다 — 두 방식의 trade-off 실물. 12차에서 채점기 속을 본 중급반에겐 "/api/score 뒤가 이 표" 한 줄 가능(초급 앞에선 생략).

### B-8. 패턴 4의 출처와 프레임워크 (슬라이드 19)
오늘의 넷은 업계에서 널리 쓰는 분류와 대응한다 — 줄 = prompt chaining, 나눔 = parallelization, 감독 = orchestrator-workers, 되돌림 = evaluator-optimizer. 같은 분류에서 routing을 별도 패턴으로 세기도 한다(오늘은 '보내기'로 분리해 Part 3). **멀티에이전트 프레임워크**(LangGraph · CrewAI · AutoGen · OpenAI Agents SDK · Claude Agent SDK 등)는 이 패턴들을 코드로 쓰게 해 주는 도구 — 이름이 뭐든 패턴 4는 같다. 한 줄: "지휘자를 코드로 쓰는 도구들, 모양은 오늘 넷 그대로."

### B-9. 두꺼운 지휘자가 생기는 경로 (슬라이드 21)
예외 처리를 지휘자에 계속 덧붙임 → 일꾼 규칙과 중복 → 충돌. 해법은 예외를 일꾼 지침 또는 라우팅 표로 내려보내는 것. "지휘자에 if가 늘면 신호."

### B-10. 서브에이전트의 컨텍스트 분리 (슬라이드 22)
작업대의 서브에이전트는 별도 컨텍스트에서 실행되고, 부모 세션에는 최종 결과(요약)만 돌아온다. 부모의 대화·읽은 파일은 전달되지 않으므로 필요한 정보는 **요청문에 명시하거나 파일 경로를 넘겨야** 한다. 이 구조가 곧 '감독 패턴'이며, 컨텍스트 분리가 비용·안정성의 이유다. **강사는 수업 전 직접 확인**(§F).

### B-11. 가드레일 (슬라이드 23)
관문의 자동판. 입력(위험 요청 차단)·출력(개인정보·금지어 검사)에 규칙을 두고 걸리면 사람 관문으로 보낸다. 사람 관문과 가드레일은 대체가 아니라 층 — 가드레일이 거르고 사람이 결정.

### B-12. 자동화와 에이전트의 관계 (부록 31)
자동화(5차 BATLR·8차 PILOT)는 **겉**의 문제 — 누가 누르나(사람/시간/이벤트), 언제 도나. 에이전트는 **속**의 문제 — 안에서 누가 판단하나. 자동화 안에 에이전트가 들어갈 수도(영상 공장), 프로그램만 들어갈 수도(엑셀 매크로). 격자로 답한다.

## §D. 여정 대체 소재 (직무 편향 완화 — 16·24에서 마케팅 대신 읽을 때)

| 직무 | 여정 ① 정상 요청 | 여정 ② 섞인 요청 | 표에 적히는 한 줄 |
|---|---|---|---|
| 마케터 (기본) | "광고 소재 3개 뽑아 주세요" | "지난달 소재 중 성과 좋았던 거 비슷하게 다시" | 성과 먼저, 그 결과로 소재 (줄) |
| 인사·총무 | "재직증명서 한 부 부탁드려요" | "재직증명서 급해요, 그리고 작년 연차 며칠 남았죠?" | 증명서와 규정은 따로 — 둘 다 보낸다 (나눔) |
| 영업·CS | "A제품 100개 견적 주세요" | "지난번 견적 조건으로 수량만 두 배로" | 과거 사례 먼저 찾고, 그 조건으로 견적 (줄) |

읽는 법은 동일 — 접수 → 종류 판정 → 담당 → 결과 → 기록 / 섞임 → 사람 → 표 한 줄 → 다시 → 두 이름. 직무별 예시(11·17·24)의 직무 3종과 같은 셋이라 연결된다.

## §E. FAQ 10

1. **"그래서 Claude Code가 에이전트인 거죠?"** — 작업대입니다. 머리·손·루프를 빌려 줍니다. 여러분 몫은 규칙·일꾼·보내는 표·남기는 곳(슬라이드 09). 속을 따지면 에이전트의 한 사례이기도 하지만, 오늘은 그걸 망치로 씁니다 — 망치가 뭘로 만들어졌는지보다 망치로 뭘 만드는지가 오늘 주제. (3분 이상 쓰지 않는다)
2. **"내 에이전트는 어디서 돌아요?"** — 오늘 수준에선 작업대 안에서. 무인으로 옮기면 엔진만 갈아끼운다 — 격자의 도구 칸 → 서비스 칸(8차 MCP now → API later).
3. **"에이전트 = 자동화인가요?"** — 자동화는 겉의 문제(누가 누르나·언제 도나), 에이전트는 속의 문제(누가 판단하나). 자동화 안에 에이전트가 들어갈 수도, 프로그램만 들어갈 수도.
4. **"claude.ai 프로젝트는 에이전트인가요?"** — 지침은 있지만 손과 루프가 없으면 LLM 칸. 손이 붙는 순간 한 칸 내려간다.
5. **"라우팅은 패턴 넷에 안 들어가요?"** — 라우팅은 '어느 줄에 세우나', 패턴은 '그 줄의 모양'. 둘은 짝. 라우팅을 다섯째 패턴으로 세는 분류도 있다.
6. **"일꾼끼리 머리를 공유 못 하면 불편한 거 아닌가요?"** — 불편해 보이지만 그게 머리 한계(병 ①)를 푸는 방법. 각자 머리가 작게 유지되니까. 필요한 건 요청문이나 파일로 넘긴다.
7. **"기본 경로를 또 다른 AI로 하면 안 되나요?"** — 가능하지만 그 AI도 모르면? 끝은 항상 사람.
8. **"클레임 답을 AI가 하면 안 되나요?"** — 답은 AI가 써도 되지만 보내기 전엔 사람. '밖' 관문(23).
9. **"우리 일은 패턴 넷이 다 섞여 있어요."** — 맞다, 20에서 섞인다고 했다. 가장 큰 뼈대 하나만 고른다.
10. **"실제로 만들어 보여 주세요."** — 다음 회차가 그날. 오늘 이름 없이 만들면 그때 뭘 고쳐야 하는지 모른다. (원칙 1 — 현재형 금지)
